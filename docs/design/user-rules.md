# User rules

`ljos prefer` and `ljos rule` already store standing instructions, and their MCP tools `ljos_prefer` and `ljos_rule` write the same atoms. A preference is prose in the seat's pack. A rule is an argv glob with a deny or ask verdict, checked by `validate_rule` and enforced by `static_guard` through `verdict_for`. Both are pack atoms. The pack stamps a review date, a missing or elapsed date counts as due, and the sweep lapses a review past twice its interval. The prompt hook then shows at most three memories, and only ones that share words with the cue. A lesson such as "never post or reply to Alan (ocaisa)" therefore comes due in a day and is easy for the next seat to miss.

User rules extend those two commands. They are not a second store with its own verbs.

A user rule is a row in `$XDG_CONFIG_HOME/ljos/user-rules.json`, the same config layer as `harnesses.toml`. When `XDG_CONFIG_HOME` is unset or not absolute, the file is `~/.config/ljos/user-rules.json`. When the file is missing, there are no rules and a covered GitHub write is allowed. An empty file, a file of only whitespace, and a dangling symlink are a bad file. A covered GitHub write is then refused, and the message names the path. A file that parses with no rows allows a covered write. Every seat on this machine reads that one file, and the same rows are carried to the other machines by the tracker repository `ljos sync` already pulls and pushes. `LJOS_SEAT` and `PACKSET_WORKSPACE` do not change the path. The file is not a pack atom, so `due_of` and the pack sweep never see it. A row has no `due_at`. A local sweep that drops only rows whose `due_at` is already past leaves an ordinary user rule in place, which is how a far-future timestamp is shown not to decay it. The row is never counted as due. Packset is the wrong store for this: a seat's pack is not shared with the other seats, and a pack atom takes a review date. deedar holds evidence, not standing rules. The tracker is the checkout that already travels between the laptop, the shared box, and the other machines.

Each machine writes only its own `.ljos/user-rules/<host>.json.age` in that repository, sealed with age to the recipients the repository's `.ljos/sync.toml` names. That is the split and the seal `ljos sync` uses for atom logs, so git does not have to merge one document and the remote never holds a rule in plaintext. Nothing leaves the machine unless that file names a scope. With none, a sync reads the rule files already in the checkout and writes nothing there. A sync fetches the tracker, reads every host file, and merges those rows with the local file. The merge key is the rule id. The row with the newer `updated_at` wins, and that winning row keeps its author and its reason. A deletion is a tombstone on the same id, `deleted` set and `updated_at` moved forward, so an older copy of the rule does not come back. The merged rows, tombstones included, are written back to the local file and sealed into this machine's host file, and that file is committed and pushed. That git runs in the tracker checkout. An exported `GIT_DIR`, `GIT_WORK_TREE` or `GIT_INDEX_FILE`, which a git hook or a worktree script sets, is dropped first, so the fetch, the merge, the commit and the push never reach the repository that started ljos. None of those calls runs a hook from the repository, the login's `core.hooksPath` or `ljos git-hooks install`, so a sitting gate that refuses a commit outside a tracker checkout does not stop the exchange. The push still runs the pre-push `ljos cloud up` installs, from the directory it was installed in, because that hook is the destination check on a cloud seat. A plaintext `<host>.json` from before the seal is still read, and this machine's own is removed in the same commit. `LJOS_TRACKER_GIT=commit` keeps that commit local and `off` leaves the tracker alone, except under `ljos prefer --user --sync`. `LJOS_USER_RULES_SYNC=off` stops the pass altogether. The tracker is the one named by `repos` in `~/.config/ljos/sync.toml`, otherwise `VISSUE_ROOT` or `ISSUE_ROOT`, otherwise the seat's vissue config, otherwise the working directory when that directory is itself a tracker.

Each row holds an id, the prose, the author, a reason, the time it was written, and `updated_at`. The id is chosen once, when the row is created, and a merge does not mint a new one. The author is the holder running the command. The reason is required. A row written with `ljos rule --user` also holds `pattern` and `verdict`, under the same checks as a seat rule. A row that names a person for the outbound-post guard holds two structured fields, `deny_mention` and `deny_reply_to`, each with `handles` and `names`. The guard never scans the prose. Empty structured fields mean the prose is for the model, and an argv pattern, if any, is the only law.

Only an explicit command writes a row. `ljos prefer --user TEXT --why REASON` writes the prose and does not also post a seat preference. `--deny-mention`, `--deny-name`, `--deny-reply-to` and `--deny-reply-name` fill the structured fields and may be repeated. `ljos rule --user PATTERN --verdict deny|ask --why REASON` writes the argv law into the same file and does not post a seat rule. On `ljos_prefer` and `ljos_rule`, the same write happens only when `user` is true, and `why` is required. Without that flag the tools keep writing the seat pack. `ljos remember` cannot write a user rule. `ljos prefer --user --forget ID` writes a tombstone for that id and leaves the author and the reason on it. `ljos prefer --user --sync` runs one pull and push and prints what it did. A write runs the same pass after the local file is saved. Session start runs it before the preface is built. Both passes are bounded. A fetch or a push that does not return in time is killed, the hook does not wait, and the preface is the local file.

`ljos prefer --user --promote LESSON_ID --why REASON` reads that lesson from the seat pack, copies its text into a user rule with the current author and the given reason, and leaves the lesson in the pack. The lesson's review date is not copied. The command refuses a missing id, an atom that is not a lesson, and a missing reason. Tests pass a fixture lesson. They do not open a live store.

The brief, the session-start line and the per-prompt hook each begin with these rules, ahead of seat preferences and lessons. Tombstones are not part of that text. The session-start line is built after the bounded sync, so a tracker that did answer is already in the local file, and a tracker that did not answer leaves the previous local file in place. The preface is at most 1200 characters. Rules that do not fit are counted in a trailing line, and the first rule is kept even when it has to be shortened. User rules are not marked seen and are not part of the three-memory cap, so a short cue or an empty pack does not hide them. Claude Code, Codex and opencode reach the text through `ljos hook`: session start prints it, and the prompt note prints it again. agy's first model call prints the session line, and later prompts print the note. `ljos_brief` prints the same preface at the top of the brief, which is the ljos-mcp path.

`static_guard` reads user rules after the seat's own file guard and the destructive-delete checks, and before the cached seat denies. An argv row uses `verdict_for`. An outbound post is denied only from the structured fields. The line is an outbound post when it is `gh` commenting, reviewing, creating or editing a pull request or an issue, or `gh api` with method POST, PATCH or PUT. A GitHub MCP tool call is an outbound post when the server or the tool name says GitHub and the tool writes a comment, review, issue or pull request. Reads (`get_`, `list_`, `search_`, names containing `_read`) are left alone. A mention is `@handle`, or a name as a whole word, in the body or the title. A reply is the handle or the name in `in_reply_to`, `in_reply_to_user` or `reply_to`, or, on a tool whose name contains `reply`, any argument value that names them. A bare comment id is not looked up, so a reply the command does not name is not denied. Cursor's `beforeMCPExecution` hook otherwise answers allow, because `preToolUse` is its usual gate. When this guard denies, that hook denies too.

`gh pr comment 12 --body 'please ask @ocaisa'` is denied. `gh api --method POST repos/org/repo/issues/comments/7/replies -f body=seen -F in_reply_to_user=ocaisa` is denied. `gh pr comment 12 --body 'tests passed'` is allowed. A rule whose prose names Alan and whose structured fields are empty denies none of these.
